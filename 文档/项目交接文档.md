## 一、项目概述与当前进度

纯 Python + PySide6 重写的 DSH 桌宠，替代原 Electron 版 dsh-pet。
分层：`src/host`（宿主通信）、`src/runtime`（UI 渲染）、`src/shared`（纯算法）。

已完成：
1. 双模通信：standalone 走 HTTP 3080，插件模式走 stdio MCP（initialize/tools/list/tools/call 全实现）。
2. 断尾求生：stdio 收到 EOF 后用 DETACHED_PROCESS 重启为独立进程。
3. 局部穿透：WS_EX_TRANSPARENT + SetWindowPos(SWP_FRAMECHANGED)，30ms 轮询，包围盒 (220,88,200,225)。
4. 光标状态机：.cur 素材，grabMouse 防丢 release，悬停/按下/松开三态。
5. 物理：重力/反弹/地面摩擦/抛掷，纯函数在 physics.py。
6. 气泡：QPainter 白底圆角，5 秒自隐；**双击气泡 = 置顶**（2026-10-26 新增）。
7. 托盘：显示/隐藏、置顶显示、退出；**双击托盘图标 = 置顶**（2026-10-26 新增）。
8. 右键级联菜单：动作按 idle/turn/drag/clicks/moves/categories/events 分组。
9. **群体模式（本次补齐）**：ALL_PETS 全局表 + 100ms tick_flock + Boids 三力 + 重叠度漫游逃逸。
10. **群体开关（本次新增）**：菜单勾选"群体行为"，关闭时"添加多开"只加 1 只，开启时加 10 只。
11. **双击主体 = 查余额 + 把 DSH 窗口提到最前**（2026-10-29，详见 7.22）。
    只在 DSH 已运行时提窗口；**大肥鱼自己仍是 topmost**，DSH 只做一次性前台提升。
    托盘/气泡双击 = 置顶（2026-10-26）。
12. **光标倾斜摇晃**（2026-10-30）：鼠标在附近移动时，肥鱼绕脚底轻微倾斜 + 水平位移。
    纯 Qt QPainter 变换，不引入 Chromium。详见 4.8。
13. **拖拽 Q弹**（2026-10-30）：拖拽拉伸 / 松手回落 / 单击弹跳。详见 4.9。
14. **单体模式碰撞框**（2026-10-30）：单体模式下多只不许重叠，推箱子式链式顶开。详见 4.10。
15. **三个菜单开关**（2026-10-30）：摇晃 / 开机自启 / 窗口置顶，统一「名称：值」写法。详见 4.6、4.11。

未完成：真实余额 API、DSH 状态锁（动画循环到状态切换）、群体模式碰撞弹开（单体已做）、抽帧全量收尾。

## 四、核心技术机制详解

### 4.1 双模通信与断尾求生
- **standalone**：`main.py` 无 `--mode` 时默认。`server.py:start_http_server(3080)` 起 daemon 线程，`POST /event` 解析事件，`GET /state` 读 counter+workStatus。
- **stdio**：`start_stdio_server()` 逐行读 stdin JSON-RPC。必须完整应答 `initialize`（回 protocolVersion 2024-11-05）、`tools/list`（暴露 dsh_event 工具）、`tools/call`。**stdout 只能写纯 JSON 一行**，调试信息一律 `file=sys.stderr`。
- **断尾求生**：stdin 循环结束时，`subprocess.Popen([sys.executable,"-u","main.py"], creationflags=DETACHED_PROCESS)` 然后 `os._exit(0)`。
  - ?? 已知隐患：Popen **未指定 cwd**，若 DSH 从非项目目录拉起，重生进程会找不到 main.py 而静默失败。修复方式：加 `cwd=os.path.dirname(os.path.abspath(__file__))`（`__file__` 指 server.py，需再上溯两级）。

### 4.2 局部点击穿透（Win32）
- 透明无边框窗口默认整矩形拦截鼠标，透明区会挡住下层。用 `SetWindowLongW(GWL_EXSTYLE)` 加减 `WS_EX_TRANSPARENT(0x20)`。
- **必须**随后 `SetWindowPos(hwnd,0,0,0,0,0,0x0037)`（含 SWP_FRAMECHANGED），否则样式不生效。
- 30ms `hit_timer` 轮询全局鼠标：在 BODY_BOX 内 → 关穿透 + OpenHand 光标；盒外 → 开穿透 + Arrow。
- 拖拽中（drag_on）强制关穿透，防止拖一半鼠标事件被吞。

### 4.3 光标状态机
- 素材：`dafeiyu/assets/cursor_grab.cur` / `cursor_grabbing.cur`，加载失败降级 Qt.OpenHandCursor/ClosedHandCursor。
- 按下：切抓握 + `grabMouse()` 锁鼠标（防快速甩出窗口丢 release）。
- 松开：`releaseMouse()`，按当前是否在 BODY_BOX 内恢复抓握/箭头。
- 悬停判定走 `hit_timer`，**不要**在 mouseMoveEvent 里判（拖拽时会打架）。

### 4.4 物理与抛掷
- `physics.py:update_physics` 纯函数：dt 上限 0.05s，重力 1400，restitution 0.78，地面摩擦 2.5。
- 拖拽时记录 (dx/dt, dy/dt) 作初速，松手乘 throw_power(1.0)，夹到 ±3600，起 16ms phys_timer。
- 落地判据：|vx|<10 且 |vy|<10 且贴地 → 速度清零停 timer。

### 4.5 群体模式 Boids（本次补齐的关键部分）
- 全局 `ALL_PETS = []`，每只 `__init__` 里 `ALL_PETS.append(self)`，`closeEvent` 里 remove。
- 每只自带 `flock_timer`（100ms）→ `tick_flock()`。
- `tick_flock` 流程：
  1. 开关检查：`not FLOCK_ENABLED` 或 `drag_on` 或 `len(ALL_PETS)<=1` → 直接 return。
  2. 收集其他可见宠物中心点 → mates。
  3. `overlap_ratio()` 算重叠度。
  4. 若 `roam_ttl<=0`：`get_roam_probability(ov)` 得概率，乘 0.15 作每 tick 触发率，命中则 `flock_force()` 取方向，设 `roam_ttl=1200~2000ms`。
  5. `roam_ttl>0` 时每 tick 沿 roam_dx/dy 位移 6px，夹在屏幕内，同步气泡位置。
- **调参入口**：`tick_flock` 里的 `*0.15`（触发率）、`*6`（速度）、`randint(1200,2000)`（持续时间）。

### 4.6 右键菜单结构（当前实际顺序，2026-10-30 更新）

以主体菜单为准（子体只是把末尾「退出桌宠」换成「关闭本只」）：

```
打开 DSH / 关闭 DSH        （DSH 在跑时显示「关闭 DSH」，否则「打开 DSH」）
查看余额
行为：群体 / 单体          （点击切换，名称即状态，无勾选框）
多开十只 / 多开一只        （按当前行为模式追加，不是切换模式）
关闭所有（N）
摇晃：开 / 关              （全局，2026-10-30 新增）
开机自启：开 / 关          （读注册表，仅主体可点，2026-10-30 新增）
置顶：开 / 关              （全局，2026-10-30 新增）
DSH拷问：未安装 / 开·未生效 / 开 / 关   （纯文字状态，仅主体可操作）
───
大小 ?（迷你/小/中/标准/大/特大/自适应）
───
动作 ?（待机/转向/拖拽/点击回应/移动/各分类/事件动画）
───
退出桌宠（主体）/ 关闭本只（子体）
```

- **统一写法**：所有开关类菜单项都是「名称：值」的纯文字，**点击切换、名称即状态、不用勾选框**。新增开关请照这个格式，别用 `setCheckable(True)`。
- 旧版的"回到初始位置"已按要求删除；`reset_position()` 方法也在 2026-10-21 清理中一并删除了（详见 7.20）。
- `FLOCK_ENABLED`（行为模式）是 `window.py` **模块级全局变量**（不是类属性），`toggle_flock` 里用 `global` 改写。
- 各开关的状态来源**故意不统一**，取决于"哪种来源最不容易骗人"（见下表）。
- 「技能」一格的拷问开关详见 4.7。

| 开关 | 状态来源 | 为什么这么选 |
|---|---|---|
| 行为（群体/单体） | 进程内模块级变量 | 临时模式，重启回默认单体就够 |
| 摇晃 | 进程内 `_SWAY_ENABLED=[True]` | 同上，且"临时别晃"是即时诉求 |
| 开机自启 | **注册表** `HKCU\...\Run\DaFeiyuPet` | 用户在任务管理器禁用后，菜单必须如实反映（详见 4.11.1） |
| 置顶 | 进程内 `_TOPMOST_ENABLED=[True]` | 重启回默认置顶，符合"平时就该浮在上面" |
| DSH拷问 | **磁盘** `~/.dsh/AGENTS.md` + 技能目录 | 详见 4.7 |

### 4.7 拷问模式开关（2026-10-21 新增，2026-10-29 重大修正）

**需求**：把 grill-me 纳入桌宠右键菜单，一个「DSH拷问（开/关）」菜单项控制启停。

#### ★ 2026-10-29 修正：为什么"从来没生效过，除非特意去说"

**用户报障**：菜单里开了，但除非主动说"拷问我"，否则从不触发。

**根因（两层，缺一不可）**：

| 层 | 机制 | 只做这一层的后果 |
|---|---|---|
| ① 技能可见性 | `~/.dsh/skills/grill-me/` 目录存在 → 进入模型技能目录 | 技能只是**说明书**，DSH 不会因为它在就主动调用 |
| ② 自动进入模式 | `~/.dsh/AGENTS.md` 每轮注入的规则 | 规则在，但技能说明书不在 → 模型知道要拷问，却没有方法说明 |

**关键认知**：技能 ≠ 行为。技能的 `description` 只是"什么时候该读我"的提示，
**不是**"读到我就自动执行"。模型只有在语义匹配（"拷问我/盘问我"）时才去读它。
所以"开关即模式"必须靠 `AGENTS.md`（每轮注入的全局规则）实现，光搬目录没用。

**实现**（`src/host/skill_toggle.py`，纯标准库，无 Qt 依赖）：

**① 技能目录搬运**（原有，保留）

| 状态 | 磁盘布局 |
|---|---|
| 启用 | `~/.dsh/skills/grill-me/SKILL.md` |
| 停用 | `~/.dsh/skills/.disabled/grill-me/SKILL.md` |

- `shutil.move()` 同盘重命名，原子、不产生半截状态
- 放 `.disabled/` 而非加后缀：DSH 只扫直接子目录，`.disabled` 下的孙子目录不算技能
- **用移动不用删除**：关闭后文件原样保留

**② AGENTS.md 受管区块**（2026-10-29 新增）

在 `~/.dsh/AGENTS.md` 末尾维护一段被标记包住的规则：

```
<!-- dsh-pet:grill-mode:begin -->
## 拷问模式（由桌宠菜单控制，勿手动编辑本区块）
...用 ask_user_question 一次只问一个、先别动手实现...
<!-- dsh-pet:grill-mode:end -->
```

| 约束 | 做法 |
|---|---|
| 不碰用户内容 | 只增删**标记之间**的内容；标记之外逐字节保留 |
| 幂等 | 重复开启不会写第二份；重复关闭不报错 |
| 干净关闭 | 精确删除整块（含标记），文件与开启前**逐字节一致**（已实测） |
| 标记残缺 | 只剩一头 → `is_mode_active()` 返回 False 且**拒绝写入**，不猜用户意图 |
| 原子写 | 临时文件 + `os.replace` |
| 状态以磁盘为准 | 菜单每次由 `is_mode_active()` 现场探测，不写 settings.json |

**③ 原子性（踩到的真实 bug）**

最初实现是"目录、规则各写各的"，结果：技能目录不存在时，
`_set_skill_dir` 返回 False，但 `set_mode` **照样把规则写进去了** ——
模型被要求拷问，技能说明书却不在。已改为：

```python
if enabled:
    if not _set_skill_dir(True, root):   # 技能不可用 → 一个字节都别写
        return False
    return set_mode(True, agents)
# 关闭：先撤规则（模型立刻停止拷问），再挪目录
```

**状态定义：必须是"且"**

`is_enabled()` = 目录在 **且** AGENTS.md 有区块。
只满足一半时菜单显示 `DSH拷问（开·未生效）` —— 让状态不骗人。
（用户报障时的真实状态就是这个"半开"：目录在、规则从未写入。）

**菜单接入**（`window.py::_show_context_menu` + `toggle_grill_me`）：
- **复用「行为：群体/单体」的既有写法**：`addAction(menu_label())` + `triggered`，
  名称即状态、点击切换、**不加勾选框**。
- 技能不存在时置灰；**仅主体（`is_main`）可点**（多开共用同一份磁盘状态）。
- 气泡反馈：开启 →「之后我会先逐条问清方案再动手，直到你关掉它」；
  关闭 →「已恢复普通模式，不会再自动追问」。
- 整块包 `try/except`，异常不得影响菜单弹出。

**生效时机**：`AGENTS.md` 有文件监听，写入后**下一轮对话立即生效**，无需重启 DSH
（实测：写入后本轮即收到 system-reminder 更新）。

**独立性约束（硬要求，改动时勿破坏）**：

- `skill_toggle.py` **只用标准库**，不得引入第三方依赖；
- `window.py` **顶层不得** `import skill_toggle`，只允许在 `_show_context_menu` /
  `toggle_grill_me` 内部延迟导入；
- 菜单里整块包 `try/except: pass`，任何异常都不得影响菜单弹出；
- 只写 `~/.dsh/skills/` 与 `~/.dsh/AGENTS.md`，不得读写桌宠运行目录；
- **AGENTS.md 里只准动受管标记之间的内容**，绝不可重排/覆盖用户自己的规则。

**验证**：`tests/test_skill_toggle.py`（**56 项全绿**）覆盖：目录搬运往返、
区块增删幂等、**关闭后 AGENTS.md 与原文逐字节一致**、标记残缺时拒绝写入、
外部手动改文件能被探测、`DSH_HOME` 覆盖、半开状态显示"开·未生效"。

**已知限制**：
- 已加载进当前对话的技能，关闭后该次对话上下文里仍保留（移除的是"可被发现"，不是"已读入"）；
  但 `AGENTS.md` 区块是每轮重读的，所以"自动拷问"会立即停。
- 停用后若 DSH 未运行，仅影响下次启动。

**单击 / 双击行为**：单击播交互动作，双击 = 查余额 + 提 DSH 窗口（见 7.22）。

### 4.8 光标倾斜摇晃（2026-10-30 新增）

**需求来源**：用户看到 whale-pet（`@luweiyabo/dsh-whale-pet`）里"鼠标在附近晃，肥鱼也跟着晃"，要求 pp6 复现。

**实现**（`src/shared/tilt.py` + `window.py` 接线）是纯数学弹簧，不依赖 Qt，也不依赖 Chromium：

| 参数 | 值 | 含义 |
|---|---|---|
| `TILT_RADIUS` | 140.0 | 鼠标到这个半径内才开始有反映 |
| `TILT_TOP_EXTRA` / `TILT_BOTTOM_EXTRA` | 40 / 60 | 垂直方向的宽容度（高于/低于身体也能触发） |
| `TILT_MAX_DEG` | 3.5 | 最大倾角（照抄 whale-pet） |
| `TILT_MAX_PX` | 5.0 | 最大水平位移（照抄 whale-pet） |
| `TILT_SPRING` | 0.30 | 弹簧系数。whale-pet 用 0.14（达 90% 要 18 帧 ≈300ms，太黏），0.30 只需 6 帧 |
| `TILT_DEADZONE` | **0.015** | 死区（≈5.7px 鼠标位移）。详见下方"两次修正" |
| `TILT_EDGE_FADE` | 0.25 | 到半径边缘渐隐，避免边界处突跳 |
| `TILT_ORIGIN_Y_FALLBACK` | 0.917 | 默认旋转轴（脚底），对应 whale-pet 的 `FEET_Y/CANVAS_H = 330/360` |

变换输出：`translateX(cur*5px) rotate(cur*3.5deg)`，旋转轴在**脚底**（不是中心），这样才有"身体绕脚晃"的物理感。

**作用域（重要）**：
- 单体模式：主体 + 子体都晃。
- 群体模式：**只有主体晃**，子体不晃（`tilt_enabled()` 里直接 return False，`_tick_tilt` 0.49us 就退出）。
- 拖拽中 / 物理飞行中 / 窗口隐藏 / 摇晃开关关闭 → 一律不晃。

**两次实测修正（都是用户报障后定位的）**：

1. **"心跳式抽动"**：`step()` 原来收敛后无条件 `cur = 0.0`，于是 收敛(≈60帧) → 归零 → 重新收敛 → 再归零，周期约 0.86 秒，看起来像心跳。
   修法：**区分目标是否为 0** —— 目标非零时 `cur = tgt` 并 return False（不重绘）；目标为 0 才收成 0 停机。验证：静止 300 帧重绘 0 次、偏差 0.000000000。
2. **"倾斜像固定值，一格一格跳"**：`TILT_DEADZONE` 原为 0.04，在 480 宽窗口下 = 鼠标横移 **15.2px** 倾斜才变一次。
   修法：`TILT_DEADZONE` 降到 0.015，并加**滞回 + 同向直通**：
   ```python
   same_dir = (d > 0 and _last_dir > 0) or (d < 0 and _last_dir < 0)
   if same_dir or abs(d) >= TILT_DEADZONE:
       # 更新目标
   ```
   即同向移动时不受死区限制（跟手），只有反向/抖动才用死区挡。实测：缓慢单向移动 100 步仅 2 步无变化（原 50 步）；±1px 抖动只变 1 次、±2px 2 次。

### 4.9 拖拽 Q 弹（2026-10-30 新增）

照抄 whale-pet 的三个机制，全在 `src/shared/jelly.py`：

| 机制 | 参数 | 说明 |
|---|---|---|
| 拖拽拉伸 | `DRAG_SPEED_TO_STRETCH=0.09`、`DRAG_STRETCH_MAX=0.16`、`DRAG_STRETCH_SPRING=0.30`、`DRAG_STALE_MS=200` | 按拖拽速度沿运动方向拉伸 |
| 松手回落 | `SETTLE_DURATION=0.5`、`SETTLE_SX0=1.09`、`SETTLE_SY0=0.90`、`SETTLE_MID_T=0.45` | 0.5s 的回弹曲线：先压扁再弹回 1:1 |
| 单击弹跳 | `POP_DURATION=0.42`、`POP_AMP=0.06` | 点击时弹一下（视作放大再回缩） |

**关键顺序**：松手时先 `drag.reset()` 再 `settle.start()`（对标 whale-pet 的 `fxDragReset()` → `fxSettle()`），否则拖拽的形变会覆盖回弹。

**踩过的坑：整只往右弹**。纯 `scale()` 只 `translate y` 没 `translate x`，而 Qt 的缩放以原点为中心 → 放大就把图形往右下推，实测右漂 22px（单击弹跳 15px）。
修法：缩放锚点改成 `图形中心x + 底边y`：
```python
_px = x + pw / 2.0     # 水平锚在中心
_py = y + ph           # 垂直锚在底边（脚）
```
改完漂移归 0，`tests/test_jelly_window.py` 有专门回归项。

**变换栈顺序**（paintEvent）：镜像 → squash（落地压扁）→ 倾斜 → Q弹。三者共用同一个 painter 变换，不能各自独立 translate。

### 4.10 单体模式碰撞框（2026-10-30 新增）

**需求**：单体模式下多开的多只肥鱼**不许重叠**。

**规则（用户逐条确认过）**：
- 硬碰撞，不是软推开的分离力。
- 撞者继续前进，被撞者被**同向顶走**（推箱子）。
- 被顶到屏幕边缘 → 整条链一起停（不能穿墙、也不能挤压）。
- **只单体模式生效**；群体模式一行不改（群体用自己的 Boids 分离）。
- 拖拽中 / 物理飞行中豁免（否则扔出去的鱼会卡在半空）。
- 只有双方**都是单体**才碰撞。

**实现**（`src/shared/flock.py`，纯函数，不依赖 Qt）：

| 函数 | 作用 |
|---|---|
| `aabb_contact(ax,ay,ahw,ahh,bx,by,bhw,bhh,ux,uy)` | 用 **Minkowski 和**求沿方向 u 的首次接触距离 |
| `resolve_push(mover, mates, dx, dy, clamp_fn)` | 推箱子求解，返回 `(new_cx, new_cy, pushes)`；内部 `_advance()` 递归处理链式传递、`_unstick()` 处理起手就重叠 |
| `separate_overlaps(entries, clamp_fn, iterations=3, max_step=8.0)` | 全局兜底分离：每帧最多挪 8px（防瞬移），沿穿透最浅轴各退一半；一方贴墙则另一方退全部 |

**两个必须记住的修正**（都是"看起来推不动"的真凶）：
1. `if t_exit <= 0: return None` —— 贴边时 `t_exit` 可能恰为 0，不排除会误判成"永久接触"，链式推空转。
2. 撞人者的位置必须**跟随被撞者的推进量一起更新**：`state[key][0] += ux * pushed`。只更新被撞者，撞人者位置不落，表现为"撞上去没反应"。

**window.py 接线**：`collide_participates()`（群体/拖拽/飞行三段豁免）、`body_aabb()`、`clamp_body_center()`、`apply_body_center()`、`_collide_mates()`、`_resolve_move_with_collision()`。
结算点有两处 + 一处兜底：`_after_action_switch` 的 move 分支选目标点时结算一次、tick 插值后再夹紧一次、`_tick_all()` 末尾调 `_settle_single_collisions()`。

**测试环境限制**：offscreen 虚拟屏只有 **800×800**，测试坐标必须落在屏内 —— 否则被 `clamp_body_center()` 夹住，表现像"推不动"，很容易误判成算法 bug。

### 4.11 开机自启 + 窗口置顶（2026-10-30 新增）

#### 4.11.1 开机自启（`src/host/autostart.py`）

写注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\DaFeiyuPet`，值是：

```
"<pythonw.exe>" -u "<安装目录>\main.py"
```

四个决策理由：

| 决策 | 理由 |
|---|---|
| 用 **pythonw** 不用 python | 开机启动时不弹黑框（`python` 会带控制台窗口） |
| 不用 .bat / 快捷方式 | 少一层中间文件，也不会有 cmd 闪窗 |
| 只写 **HKCU** | 不需要管理员权限，也不会触发 UAC |
| 状态**以注册表为准**，不落 `settings.json` | 用户在「任务管理器 → 启动」里禁用后，菜单下次打开必须如实显示"关"，否则就是骗人 |

**残留项处理**：`is_enabled()` 会解析命令里的 `main.py` 路径并检查**文件是否真的存在**，不存在就当未启用 —— 防止桌宠挪了位置后菜单显示"开"却起不来。

**API**：`is_enabled(root)` / `set_enabled(on, root)` / `toggle(root)` / `menu_label(root)`（返回 `"开机自启：开"` / `"开机自启：关"`）。
`root` 传的是 `frames/` 的**上一级**（程序根），`_app_root()` 里自动纠正两种传法。

**非 Windows** 所有函数安全返回 `False`，不抛异常。

**只允许主体操作**：多开个体共用同一份系统状态，各自切换会互相打架 → 菜单项 `setEnabled(bool(self.is_main))`。

#### 4.11.2 窗口置顶（`window.py`）

原来 `WindowStaysOnTopHint` 是**硬编码永远开**，本次改成可切换：

```python
_TOPMOST_ENABLED = [True]          # 默认 True = 保持改造前行为
topmost_enabled() / set_topmost(on) / _apply_topmost_to(widget, on)
```

**三个必须改的"绕过开关"的地方**（只加菜单项不改这三处 = 关了会被偷偷改回去）：

| 位置 | 原代码 | 改为 |
|---|---|---|
| `bring_to_front()` 的 Qt 层 | `setWindowFlag(Qt.WindowStaysOnTopHint, True)` | `topmost_enabled()` |
| `bring_to_front()` 的 Win32 层 | `HWND_TOPMOST(-1)` | `-1 if topmost_enabled() else -2`（NOTOPMOST） |
| `PetWindow.__init__` / `BubbleWindow.__init__` | 硬编码 `WindowStaysOnTopHint` | 按 `topmost_enabled()` 条件拼接 |

否则：关掉置顶后双击一下桌宠（走 `bring_to_front`）又把置顶设回去了；多开的新个体也还是最上层。

**Qt 的坑：`setWindowFlag()` 会隐藏窗口**。改完 flag 原生窗口可能被重建，几何位置有概率被重置。
所以 `_apply_topmost_to()` 的顺序是：
```python
geo = widget.geometry()
was_visible = widget.isVisible()
widget.setWindowFlag(Qt.WindowStaysOnTopHint, bool(on))
if was_visible:
    widget.show()
    widget.setGeometry(geo)     # 还原位置
```
实测切换前后位置稳定在 `(100,200,480,270)`、窗口全程可见。

**作用范围**：所有个体 + 每个个体的气泡，一起切（`ALL_PETS` 遍历）。

### 7.5.3 漫游算法：补 5 处（这是"能不能散"的关键）

| # | 补什么 | 为什么 |

| 1 | **首次移动强制 360° 随机**（`_first_move_random`） | 一批副本起手的 facing/微小合力几乎一致，走涌现判定极易被统一成"齐步走" |

| 3 | **预输入不打断**（`_pending_force_roam_at`，TTL 2500ms） | 原来 `ov>=0.8` 直接 `load_next_action()` 会把正在播的动作**半途截断**，10 只同时命中就是集体跳帧 |
| 4 | **大池等概率**（`pick_big_pool_equal`） | 群体模式下非移动动作应对齐 dsh-pet 的 `pickBigPoolAction`：idle+turn+全部 categories 平分，而不是按权重 |
| 5 | **基础距离 80~240 → 60~240** | 对齐 dsh-pet `moves.default`（60~240） |

另外把多开落点从"依次错开 40px"改成**全部叠在屏幕正中**（`spawn_idx > 0` 也走正中分支）——
这是刻意设计，人工错开反而削弱"一起炸开"的爆发感。

## 七点六、2026-10-17 深夜：30 只卡顿的性能修复

> 现象：大肥鱼能开 70 只、Electron 版 pet 能开 60~70 只，pet-pyside6 **30 只就严重卡顿**。
> 结论：两个根因，都在"帧"上，与渲染后端、GPU、碰撞逻辑无关。

### 7.6.1 根因一：整动作帧全驻留（内存）

| | 大肥鱼 | pet-pyside6 改造前 |
|---|---|---|
| 帧驻留 | `DECODED_FRAME_CACHE = 24`，**有界 LRU** | 整个动作 **241 帧全转 QPixmap 常驻** |
| 单只内存 | 24 × 640×360×4B ≈ 22 MB | 241 × 640×360×4B ≈ **222 MB** |
| 30 只 | 每只一个进程，各自 22MB | **≈ 6.6 GB**（单进程） |

大肥鱼源码注释写得很直白："24fps 全驻留需要超过 1GB，所以改成按需读字节 + 有界缓存解码"。

### 7.6.2 根因二：启动瞬间 30 个解码线程

30 只同时切动作 → 各自 new 一个 `LoadThread` 解码同一份 241 帧，
而帧缓存要等解码完成（`on_loaded`）才写入 → **缓存救不了这次并发**。

实测：启动瞬间 **RSS 6.7 GB / CPU 740%**，之后才回落到 580MB —— 那几秒就是"卡死"观感。

### 7.6.3 三项修复

| # | 改动 | 文件 |
|---|---|---|
| 1 | 帧按 **(动作, 宽, 高)** 进进程级缓存，**预缩放到显示尺寸** | `src/runtime/frame_cache.py`（新增） |
| 2 | `paintEvent` 改为 **1:1 贴图**，去掉每帧 `SmoothPixmapTransform` 重采样 | `src/runtime/window.py` |
| 3 | 同动作解码**去重**（`_INFLIGHT` 表）+ 解码并发上限 3 | `window.py` / `loader.py` |

> **共享的是帧数据，不是动作**：每只照常随机挑自己的动作，只是碰巧挑到同一动作时
> 复用同一批 QPixmap（QPixmap 隐式共享，不复制像素）。动作多样性不受影响。

### 7.6.4 实测（30 只）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 启动峰值 RSS | 6.7 GB | **733 MB** |
| 启动峰值 CPU | 740% | **133%** |
| 稳态 RSS | ≈ 6 GB | **580 MB** |
| 稳态 CPU | 高 | 20~40% |
| 缓存命中 | — | hit 93 / miss 10 |

### 7.6.5 调参与环境变量

- `DSH_PET_FRAME_CACHE_ACTIONS`（默认 3）：同时驻留几个 (动作, 尺寸)。调小更省内存但会增加重解码。
- `loader.MAX_CONCURRENT_DECODE`（默认 3）：同时解码的动作数。
- **scale 变化会让缓存 key 失效**，重新缩放一次（`setFixedSize` 后自动重新加载当前动作）。

### 7.6.6 还未做（如果以后要上 70 只）

- 单进程 GUI 线程仍然是串行的：paint + 定时器都在这一个线程。
- 若要逼近大肥鱼的 70 只，下一步是**每只一个进程**（和大肥鱼同构），
  代价是群体状态要跨进程共享（大肥鱼用 `dafeiyu-flock.json`）。
- 或者保持单进程，把"帧推进"合并到**全局单一定时器**（现在每只一个 `timer`）。

## 七点九、抛掷物理 / 弹性碰撞 / 拖拽优先级

> 之前 `physics.py` 写好了但**从未被调用**，`mouseReleaseEvent` 只是 `load_next_action()`——
> 也就是说：松手不会飞、没有重力、没有反弹。已按 pet 的参数补齐。

### 7.9.1 参数（与 pet 的 `shared-core.js` 同值）

```python
GRAVITY = 1400.0          # px/s²
RESTITUTION = 0.78        # 弹性
GROUND_FRICTION = 2.5     # 落地摩擦
REST_VX = 15.0 / REST_VY = 40.0   # 静止阈值
MAX_STEP_DT = 0.05        # 单步上限
MAX_THROW_SPEED = 3600.0  # 初速上限
MIN_THROW_SPEED = 220.0   # 低于它只算放下，不抛
```

### 7.9.2 链路

```
mousePress   → 停物理 + 记录轨迹起点 + force_action(拖拽悬空动画)   ← 最高优先级，打断一切
mouseMove    → 跟随 + 采样 (t, x, y)
mouseRelease → estimate_release_velocity(最近 150ms) → start_throw(vx, vy) 或原地放下
start_throw  → 16ms phys_timer → tick_physics
tick_physics → update_physics（重力/边缘反弹/落地摩擦）→ 静止后回动作链
```

### 7.9.3 优先级

- `load_next_action()` 开头：`if self.drag_on or self.phys_timer.isActive(): return`
  —— 拖拽与飞行期间**不换动作**，拖拽最高优先级。
- `tick()` 里 `idx >= n` 且 `drag_on` 时：`idx % n` **循环播放**拖拽悬空动画（不切走）。
- `tick_flock()` / `poll_state()` 原本就有 `drag_on` 守卫。

### 7.9.4 边界照搬 pet（解决"透明边撞墙"）

**问题**：窗口 640×360，身体只占中间 217px 宽，左右各有 ~210px 透明边。
如果按整窗口夹屏，身体永远走不到屏幕边缘，看起来像"隔着一层看不见的墙"。

**pet 的做法**（`throwBoundsIn`）：

```js
const throwBoundsIn = (area, size, sideAllow) => {
  const h = size * 9 / 16;
  return { minX: area.x - sideAllow, minY: area.y,
           maxX: rectRight(area) - size + sideAllow,
           maxY: rectBottom(area) - h };
};
```

`sideAllow = BODY_BOX.left × scale`（身体左边距）。窗口**可以伸出屏幕 sideAllow**，
于是身体正好贴边：

```
屏幕 2560×1440，窗口 480×270，sideAllow = 210×0.75 = 157.5
→ bounds = (-158, 0, 2238, 1170)
→ 窗口左缘可到 -158，身体左缘 = -158 + 157.5 = 0  ← 精确贴边
旧实现窗口左缘最小 0 → 身体左缘 157.5，永远差 157.5px
```

已添加到 `window.py`：`throw_bounds_in(area, size, side_allow)`。

### 7.9.5 多屏：按身体中心选屏

pet 的 `throwStepRegion` 用 `screenOfBox` 逐屏取 bounds。对应实现：

```python
def _screen_at(cx, cy)      # 中心落在哪块屏就用它；屏缝/空洞取最近
def _screens()              # 所有显示器可用区域
```

`tick_physics` 与漫游夹取都改成先算**身体中心** → 选屏 → 取该屏边界。

### 7.9.6 静止判定照搬 pet 的 atRest（两式取或）

```js
atRest = (y >= maxY-1 && |vy| < 1 && |vx| < REST_VX)
      || (bounced && speed < REST_VY && |vy| < 1)
```

第二式是"刚弹跳过、总速度已很小"就收；只看第一式会因为 vy 长期不为 0 而迟迟不停。

### 7.9.7 实测轨迹（初速 700, -500）

```
t=2.03 触底 v=(672,-1133)   ← 反弹（×0.78）
```

### 7.9.5 单群分立的边界（重要）

| 逻辑 | 归属 |
|---|---|
| **拖拽**（按下立刻播拖拽动画、最高优先级打断一切、跟随移动） | **全模式共享** |
| **抛掷物理 / 弹性碰撞**（重力、边缘反弹、落地摩擦） | **单体限定**（群体松手只放下，不进物理链路） |

## 七点十、落地 Q 弹 + 反弹衰减（百分比 + 固定值）

### 7.10.1 落地 Q 弹（照搬 pet 的 landingSquash / squashScale）

触发：**只在「空中 → 地面」那一帧**（`grounded and not _prev_grounded`）。
渲染：围绕**底边**做 `scaleY`（对应 pet 的 `transform-origin: bottom`）。

```python
landing_squash(impact)  # |impact| 300→0.8（几乎不压） 1500+→0.55（压得狠）
squash_scale(u, depth)  # 前45%平方缓入压扁，后55%回弹并过冲 ≤1.12
SQ_DURATION_MS = 220
```

实测曲线（depth=0.55）：`1.000 → 0.644(88ms) → 1.043(176ms) → 1.000(220ms)`。

### 7.10.2 反弹衰减：百分比 + 固定值

```python
vy_after = abs(vy) * RESTITUTION - FIXED_BOUNCE_DECAY   # 0.78 * v - 80
```

- **只有百分比**时，离散步长下存在不动点 `v ≈ 2·g·dt/(1-E)`（16ms 时 ≈204），
  小幅弹跳会稳定在该速度**永不衰减** —— 就是"贴地后小幅度弹个不停"。
- 加固定扣减后：`1438 → 1041 → 732 → 493 → 304 → 157 → 42 → 0`，约 7 次收住。
- 大速度时百分比主导（弹性手感），小速度时固定值主导（干脆收尾）。

实测收敛（斜抛）：8ms→10.0s，16ms→6.9s，33ms→5.4s，50ms→4.9s。
调快/调慢只需改 `physics.FIXED_BOUNCE_DECAY`（默认 80）。

### 7.10.3 收尾兜底

`tick_physics` 额外加一重判定：**连续贴地 3 帧**即收（尾段小幅弹跳每帧都贴地，
正常大幅反弹离地久、计数会被重置，不受影响）。

### 7.9.8 边界语义 bug（已修）

`throw_bounds_in` 最初照抄 pet 的 `throwBoundsIn`（返回**窗口左上角上限**），
但本地 `update_physics` 的 `max_x/max_y` 是**右缘/底缘上限**（判断 `x + w > max_x`）。
两者差一个窗口尺寸，墙被往里缩：

```
屏幕 2560×1440、窗口 480×270、sideAllow 157.5
旧：maxX = 2560-480+157.5 = 2237.5 → 身体右缘只到 2080   ← 实测量到约 2070
旧：maxY = 1440-270      = 1170   → 实测量到约 1100
```

修复：返回右缘/底缘上限

```python
return (
    area.left() - side_allow,                    # 窗口左缘下限
    area.top(),                                  # 窗口上缘下限
    area.left() + area.width() + side_allow,     # ★ 右缘上限
    area.top() + area.height(),                  # ★ 底缘上限
)
```

验证：身体左缘最小 0、右缘最大 2560、底缘最大 1440（正好贴满屏幕）。

### 7.9.9 边界实时辨认屏幕边缘（不是固定矩形）

三处改动：

1. **`_scr()` 去掉缓存** —— 原来缓存了主屏几何，分辨率/缩放/任务栏变化后边界不更新；
   现在每次都实时读 `QGuiApplication.primaryScreen().availableGeometry()`。
2. **`_screens()` / `_screen_at()` 本来就实时** —— 每帧重新枚举所有显示器，按身体中心选屏。
3. **新增 `_has_screen_at(x, y)`，区分「真屏幕边缘」和「屏缝」**：

```python
if _has_screen_at(body_left - 2, cy):   bounds[0] = -1e9   # 左边还有屏 → 不设左墙
if _has_screen_at(body_right + 2, cy):  bounds[2] = 1e9    # 右边还有屏 → 不设右墙
```

单屏时四个方向都是真边缘 → 正常反弹；多屏拼接时屏缝方向放开，宠物能从一块屏滚到相邻屏，

身体左缘 0 / 右缘 2560 / 底缘 1440 —— 正好贴满。

### 7.9.10 底边向下拓 50px + 缩放自适应

**向下拓展**：

```python
BOTTOM_EXTEND = 50.0   # 物理像素，不跟随缩放
# throw_bounds_in 的底缘：area.top + area.height + BOTTOM_EXTEND
# 漫游夹取的 max_y 同步 + BOTTOM_EXTEND
```

## 七点十一、动画流畅性：完全照搬大肥鱼的播放模型

> 症状：只有几只也"莫名抽搐"，动作播个开头就被切，多开个体互相影响（但没有广播）。
> 根因有三层，全部按大肥鱼的实现重写。

### 7.11.1 三层根因

| # | 问题 | 后果 |
|---|---|---|
| 1 | **每只一个 14ms QTimer** | 30 只 = 2143 次回调/秒挤在一个 Qt 事件队列互相抢 → tick 间隔抖动 → 抽搐。多开"互相影响"也是这个原因（共享事件循环，不是广播） |
| 2 | **`_frame_accum / frame_ms` 绝对帧号 + 补帧时归零** | 补帧到达把 `cur_pix` 拍回第 0 帧、累加时间清零 → 实测帧间隔掉到 3.7ms（正常应 ≥27ms） |
| 3 | **切换/循环无过渡** | 片段之间硬跳 |

### 7.11.2 照搬的三段实现

**① 全局单一定时器**（替代每只一个）

```python
_GLOBAL_TICK = [None]
def _start_global_tick():
    tm = QTimer(); tm.setInterval(14)   # 41.7/3，与大肥鱼 sub-frame poll 同口径
    tm.timeout.connect(lambda: _tick_all()); tm.start()
def _tick_all():
    for pet in list(ALL_PETS): pet.tick()
```

**② `advance(elapsed_ms)` + `divmod`**（照搬 `animation_model.advance`）

```python
steps, self._frame_elapsed = divmod(self._frame_elapsed + elapsed_ms, self.frame_ms)
next_frame = self.frame_idx + steps
if next_frame < n:      self.frame_idx = next_frame
elif looping:           self.frame_idx = next_frame % n
else:                   self.frame_idx = n - 1; self._frame_elapsed = 0.0; return "ended"
```

余数保留，长跑不漂移；`tick` 只做「增量 → advance → 同步渲染」。

**③ 片段切换 100ms 淡化**（照搬 `crossfade_duration`）

```python
def crossfade_duration(prev, cur, drag_clips=()):
    if not prev or prev == cur or prev in drag_clips or cur in drag_clips: return None
    return 0.10
```

绘制：**旧帧不透明垫底** + 新帧 `alpha = (el/dur)**0.7` 淡入 —— 不会出现空白帧，也不会重影。

**④ 位移用 `roam_ratio`**（照搬）

```python
def roam_ratio(progress, window):
    if progress <= start: return 0.0
    if progress >= end:   return 1.0
    return (progress - start) / (end - start)
```

起步/收尾冻结，中间线性 —— 替代原来的整段 smoothstep。

### 7.11.3 附带优化

- `_screens()` 加 1 秒缓存：`QGuiApplication.screens()` 是系统调用，移动中的宠物每 tick 都调，实测会拖慢 tick
- `on_loaded` 的补帧分支：`upgrading = (name == current_name and bool(pms))` —— 同动作重播绝不重置播放进度

### 7.11.4 实测

```
帧间隔：中位 42.0ms（24fps 正确），正常间隔最小 23~27ms
淡化触发：11 次 / 40 秒（3 只），每次 0.10s
```

用户验收：**"这次顺畅了"**。

## 七点十二、单体 / 群体模式分立（调度规则）

### 7.12.1 规则

| | **单体模式** | **群体模式** |
|---|---|---|
| 抽取 | **所有动作统一进大池**（idle + turn + move + 全部 categories）等概率 | 大池只含非移动动作；漫游由 overlap 单独判定 |
| 漫游 | **绑定在动作上**：抽到移动动作就执行位移 | 按 overlap 算概率触发 |
| 实现 | `pick_big_pool_equal(..., include_moves=True)` | `pick_big_pool_equal(...)` + 涌现判定 |

### 7.12.2 曾经的错误实现（已修）

- ❌ 单体走 `roll_kind` 四档（idle 10% / turn 5% / move 5% / action 80%）—— 与"统一大池"不符
- ❌ 给单体加"25% 漫游判定"—— 多余，漫游应绑定动作而非独立判定
- ✅ 现在：单体就是一次大池等概率抽取，抽到 move 池的动作 → `cat_type='move'` → 位移

### 7.12.3 朝向判定

移动朝向**一律按实际位移方向**（`move_target_x - move_start_x` 的符号），
不信任 `steer_target` 返回的 `new_dir`——后者与最终目标点可能不一致（合力/边界修正会改目标点），
实测会出现"向右走却朝左"。

`_facing_dir` 也按 `tx - cx` 的符号修正，保持一致。

### 7.12.4 命中与菜单（同批修复）

- **启动默认隐藏**：流式加载后 `on_loaded` 走 upgrading 分支 early return，
  首次的 `show()` 永不执行。抽出 `_place_on_first_load()`，`on_first_batch` 也调用。
- **菜单一弹出就被打断**：全局 100ms 穿透检测在光标移到菜单上时判定"不在身体"→ 设穿透 →
  菜单失去输入。加 `_menu_open` 守卫，菜单期间不切穿透。
- **命中区太紧**：`BODY_BOX` 是亮度阈值实测包围盒，边缘毛发点不到。加 6px 容差（按缩放折算）。

## 七点十四、2026-10-18 下午：多开稳定性 / 菜单 / 名字气泡

### 7.14.1 召唤序号 `spawn_idx` 改成自增（关键 bug）

原来：

```python
self.spawn_idx = len(ALL_PETS)     # ← 关掉多开后计数回落
```

后果：关掉 2 只再新建，新宠可能拿到 `spawn_idx = 0` → **被误判成主体** →
"关闭全部多开时跳过主体"失效，表现为**关闭多开把主体也杀了**。

改为模块级自增：

```python
_SPAWN_SEQ = [0]
self.spawn_idx = _SPAWN_SEQ[0]; _SPAWN_SEQ[0] += 1
self.is_main = (self.spawn_idx == 0)
```

实测：`[0,1,2,3]` → 关 2 只 → `[0,3]` → 再建 3 只 → `[0,3,4,5,6]`，序号**永不复用**。

另外新增 `is_main` 布尔：全程序统一用它判断主体，比到处写 `spawn_idx == 0` 清楚。
**不能用"有没有气泡"判断**——每个 `PetWindow` 在 `__init__` 里都创建了 `BubbleWindow`。

### 7.14.2 镜像错误：`_INFLIGHT` 重复登记 + `on_first_batch` 不幂等

现象：镜像错误率**随移动个体增加而上升**（30 只后明显），表现为"倒退跑"。

根因链：

1. 同一只宠物可能被登记进 `_INFLIGHT[key]` 两次（`load_next_action` 与 `force_action` 竞争）
2. `_first_batch` 遍历 waiters → 对同一只调两次 `on_first_batch`
3. `on_first_batch` 里的 `_after_action_switch` 是 **move 分支会重新随机目标点**
4. 结果：位置朝 A 边、画面按 B 边镜像 → 倒退

两处修复：

```python
# _INFLIGHT：同一宠物只保留一条（更新 gen）
for i, entry in enumerate(lst):
    if entry[0] is self:
        lst[i] = (self, name, cat_type, msg, gen); return

# on_first_batch：同一动作 + 同一 gen 只处理一次
_tag = (name, getattr(self, '_load_gen', 0))
if getattr(self, '_last_first_tag', None) == _tag:
    return
```

实测 36 只 / 90 次移动：**镜像错误 0 次**。

### 7.14.3 关闭多开严重卡顿

根因：`LoadThread.run()` 是**纯解码循环，从不检查中断标志** →
`quit()` 无效 → `wait(200)` 超时 → QThread 在运行中被回收
（`QThread: Destroyed while thread is still running`）→ 卡顿甚至崩溃。

修复：

```python
# loader.py 的 run() 循环里
if self.isInterruptionRequested():
    return

# 关闭时
ld.requestInterruption()
ld.quit()
ld.wait(100)     # 中断后几毫秒就退出；必须先 wait 再丢弃引用
```

`close_all_pets` 也改成"先统一中断所有线程 → 再统一 close"，避免逐只等待累积。
实测关 40 只：**35 ms**（原来 20 秒量级）。

### 7.14.4 移动末尾"画面停了还在滑"

`螃蟹走路`/`原地漂浮踏步` 没配 `leadSec/tailSec`，`config_loader` 直接取
`a['params']` 得 0 → `roam_ratio` 窗口退化成全程线性。

```python

_params = dict(_move_default); _params.update(a.get('params') or {})
```

实测位移曲线（10 秒动作）：0~2s 起点冻结 → 2~8s 线性 → **8~10s 终点冻结**。

### 7.15.2 崩溃根因：退出时序

```
Thread [LoadThread]:  loader.py:63 in run      <- QImage(str(f))
Current thread:       main.py:98               <- sys.exit(app.exec())
QObject::~QObject: Timers cannot be stopped from another thread x N
```

线程与句柄交给操作系统回收（日志是行缓冲，已落盘）。副作用只有两条无害的
`QThreadStorage: entry destroyed before end of thread` 警告。

实测：反复「多开 20 只 → 300ms 后退出」6 轮（最坏情况：线程全在解码中），`crash.log` 增量 0。

## 七点十六、2026-10-19：拖拽三段化 / 工作状态排队 / 子体差异

### 7.16.1 拖拽动画三段化

素材 `被鼠标拖拽悬空反馈` **241 帧 / 10.04 秒**，逐帧测顶部 Y 得到结构：

| 阶段 | 帧范围 | 时长 | 顶部 Y |
|---|---|---|---|
| 站立 | 0 ~ 20 | 0.88s | 65（稳定） |
| 上升（站立→悬空） | 21 ~ 42 | 0.92s | 65 → 25 |
| 悬空 | 42 ~ 200 | 6.6s | 25~42（浮空摆动） |
| 落下（悬空→站定） | 200 ~ 218 | 0.75s | 42 → 65 |
| 落定 | 218 ~ 240 | 0.96s | 64 |

**切分点实测帧间差异**（相邻帧平均 1.75）：帧42↔43 = **0.21**、帧210↔211 = **0.27**，
都是动作最平缓处；首尾帧差异 3.53，落定后能自然接回站立。

```python
DRAG_STAND_END = 21
DRAG_LIFT_END  = 42
DRAG_HOVER_END = 200
DRAG_FALL_END  = 240
```

**播放规则**（用户定）：

| 时机 | 行为 |
|---|---|
| 抓起 | 播 `0→42`（站立→悬空），播完自动进悬空段 `42→200` 循环 |
| 松手且**进入抛物线**（≥`MIN_THROW_SPEED`=220 px/s） | `_drag_range=None` → **完整播放整段**，不截断 |
| 松手且**没进抛物线**（轻放） | 跳到 `200` 播 `200→240`，播完 `ended` 回动作链 |
| 飞行中 | 动画循环，物理 tick 负责位置 |

实现要点（`advance`）：

```python
rng = getattr(self, '_drag_range', None)
if rng is not None:
    seg_loop = self.drag_on or self.phys_timer.isActive()
    if not seg_loop:
        if steps_in >= span:          # 播完
            self.frame_idx = r1 - 1
            return "ended"
        self.frame_idx = r0 + steps_in
    else:
        self.frame_idx = r0 + (steps_in % span)   # 循环
```

**对所有个体生效**：全部是实例方法，没有任何 `is_main` / `spawn_idx` 判断。

**已知粗糙点**：松手时若悬空段刚开始（帧 43），跳到帧 200 有 150 帧姿态差。
可用已有的 `_fade_from` 做 100ms 淡化过渡（暂未加）。

### 7.16.2 工作状态动画改为排队（不再硬插）

原实现 `poll_state` 里状态一变就 `force_action`，会把正在播的动画拦腰截断
（DSH 状态变化频繁时表现就是"工作状态动画打架"）。

改为：

```python
# poll_state：只排队，后到覆盖先到，只留最新
self._pending_ws = (anim_name, msg)

# tick 里 advance 返回 ended 时才播
pending = self._pending_ws
if pending is not None:
    self._pending_ws = None
    name, msg = pending
    if name != self.current_name:
        self.force_action(name, msg)
```

优先级：**拖拽 > 完整播放当前动画 > 排队的工作状态 > 随机链**。

实测（连发 3 次状态变化）：动画只被打断 1 次，且是在 `frame=240`（241 帧播完）时。

### 7.16.3 子体差异（本次明确）

| 能力 | 主体 | 子体 |
|---|---|---|
| 拖拽三段 / 抛掷物理 / 名字气泡 / 菜单 / 大小 | 是 | 是 |
| **工作状态动画 + 排队** | 是 | **否** |

`poll_state()` 第一行就 `if spawn_idx != 0: return` —— 子体根本不读 DSH 状态。
所以 `_pending_ws` 永远是 `None`。拖拽清 pending 那行也加了 `is_main` 判断：

```python
if getattr(self, 'is_main', False):
    self._pending_ws = None
```

### 7.16.4 菜单与大小

- **主体**菜单最后一项：`退出桌宠`（退出整个程序）
- **子体**菜单最后一项：`关闭本只`（`close_self()`，只关自己）
- **新多开继承主体大小**：`PetWindow(..., scale=float(self.scale))`
  —— 创建时就设好，不会"先按默认大小出现、再缩一下"

## 七点十八、2026-10-21：双击查看余额

> 需求：单击仍是"触发交互动作"，**双击改成查看余额**。

### 7.18.1 实现在 `mouseReleaseEvent` 里自己判双击

没有用 Qt 的 `mouseDoubleClickEvent`，原因：

- 拖拽路径里有 `grabMouse()` / `releaseMouse()`，双击事件可能被吞掉或重复派发；
- 点击判定本来就在 `mouseReleaseEvent` 的 `moved < 15` 分支里，
  在同一处比较"两次松手的时间差"最直接、不会两条路径打架。

```python
now = time.monotonic()
gap = now - self._last_click_t
self._last_click_t = now
if gap <= DOUBLE_CLICK_MS / 1000.0:
    self._last_click_t = 0.0     # 用掉这次，避免"三击"又触发一次余额
    self.check_balance()
    return
clicks = self.raw_anims.get('clicks', []) or []
if clicks:
    self.force_action(random.choice(clicks))
    return
```

`DOUBLE_CLICK_MS = 400`（`window.py` 顶部常量，在 `DRAG_*` 后面）。

### 7.18.2 行为对照

| 操作 | 结果 |
|---|---|
| 单击 | 随机播一个 `clicks` 池里的回应动作 |
| 双击（间隔 ≤300ms） | `check_balance()` —— 余额气泡 + 余额动画 |
| 三击 | 第 3 击算新一轮第一击 → 播动作（不会连续弹两次余额） |
| 拖动超过 15px | 走拖拽/抛掷，不触发点击逻辑 |

### 7.18.2b 拷问后定的细节（2026-10-21）

用 `grill-me` 逐条确认过，最终取舍：

| 议题 | 决定 | 理由 |
|---|---|---|
| 双击窗口 | **300ms**（不是 400/500） | 多数人双击间隔 150~250ms；500 是系统默认但多数人把滑杆调快了，400 会让手慢的两次单击被吞 |
| 第 1 击是否播动作 | **播** | 不做延迟判定，单击零延迟；300ms 内打断一次动作观感可接受 |
| 多开子体双击 | **转发给主体**，由主体弹气泡 | 余额是全局数据；气泡始终从没编号的那只出来，多开时不会混淆 |
| 独立运行（无 DSH） | **降级为播动作**，不弹"未连接"气泡 | 双击是个交互手势，没数据时不该只回一句错误 |
| 拖拽后计时 | **不清零** | 拖拽必然耗时远超 300ms，天然不会与之前的点击构成双击 |
| 单击后极快拖 16px 松手 | 接受可能误判成双击 | 边角情况，代价只是多弹一次余额，不值得加代码 |
| 余额动画 | **与右键菜单完全一致**（动画 + 气泡） | 同一个 `check_balance()` |

实现拆成两个小方法：

```python
def _balance_available(self):   # 快照有没有推过来
    snap = self.store.get_balance() if self.store else None
    return bool(snap) and snap.get('status') not in (None, 'disabled')

def _request_balance(self):     # 主体自己弹，子体转发
    if self.is_main:
        self.check_balance(); return
    for pp in ALL_PETS:
        if pp.is_main and pp.isVisible():
            pp.check_balance(); break
```

双击弹余额 / 双击第 1 击仍播动作 / 三击不重复弹余额 / 三击第 3 击播动作 /
慢速两次单击 = 2 次动作 / 拖动不触发点击。

## 七点十九、2026-10-21：动作完整播放保护

> 需求："完整播放当前动作这条规则只能被交互打断"。

### 7.19.1 原来的两个非交互打断源

| 触发点 | 频率 | 原行为 |
|---|---|---|
| `_fire_whisper`（碎碎念） | 每 3~8 分钟随机 | 直接 `force_action`，**播到一半就换** |
| `_end_spawn_hold`（召唤散开） | 启动后 2 秒 | 直接 `load_next_action`，可能打断 |

工作状态本身是排队等播完的，但动作先被上面两个打断后，观感上就像"被工作状态打断"。

### 7.19.2 机制

```python
def _action_incomplete(self):
    """当前动作是否还没播完（至少一遍）。"""
    t0 = getattr(self, '_action_t0', 0.0)
    dur = getattr(self, '_action_dur', 0.0)
    if not t0 or dur <= 0.0:
        return False
    return (time.monotonic() - t0) < dur * 0.97

def force_action(self, anim_name, msg="", interrupt=False):
    if not interrupt and self._action_incomplete():
        self._queued_action = (anim_name, msg)   # 排队，不打断
        return
    ...
```

- `_action_t0` / `_action_dur` 在 `on_first_batch` 用 `_mark_action_start(total)` 记录；
  补帧到达（`upgrading` 分支）时按完整帧数**更新时长**，不重置起点。
- `load_next_action` 同样加保护：未播完则记 `_pending_next`，等 `ended` 再抽。
- `ended` 分支按优先级消费：`_queued_action` → `_pending_next` → `_pending_ws` → 随机链。

### 7.19.3 谁可以打断（interrupt=True）

拖拽（按下/松手）、单击动作、**双击查余额**、右键菜单、改大小。
其余（工作状态 / 碎碎念 / 召唤散开 / 抛掷落地）一律排队。

### 7.19.4 验证

`tests/test_action_integrity.py`（6 项）：非交互只排队不切换 / 队列正确记录 /
交互立即打断 / 打断时清空队列 / `load_next_action` 未播完延后 / 播完后消费队列。

## 七点二十、2026-10-21：全面清理与一次严重误判

### 7.20.1 ★ 教训：桌宠是独立进程，改完必须重启

`window.py` 是纯 Python，**没有热重载**。改完代码只做"同步到 F 盘"是无效的，
必须 `Stop-Process` 后再启动，否则跑的还是内存里的旧版本。

> 本次因为漏了这一步，把"打开 DSH 拉不起来"误判成双击功能引入的 bug，
> 白做了一轮回滚。实际原因见 7.20.3。

### 7.20.2 为什么"打开 DSH"会静默失败

DSH 是 Electron 应用，启动时先调 `requestSingleInstanceLock()`：

```js
function claimDesktopSingleInstance(application, focusOwner) {
    if (!application.requestSingleInstanceLock()) {
        application.quit();      // ← 拿不到锁直接退出，退出码 0，无任何提示
        return false;
    }
    ...
}
```

而 `kill_dsh()` 用 `taskkill /F /T` **强杀**，DSH 来不及清理单实例锁。
下次点"打开 DSH"时，新实例撞上残留锁 → 静默退出 → 看起来像"点了没反应"。

**尝试过但已回滚的方案**（不可用，勿重犯）：在 `open_dsh` 里 `sleep(3)` 校验存活、
在 `close_dsh` 里轮询 `wait_dsh_gone(6s)`。这些是**在 Qt 主线程同步阻塞**，
直接导致关闭/打开卡死数秒；且改成"优雅关闭"（taskkill 不带 `/F`）后，
`dsh-vision-router` 的子进程不响应 WM_CLOSE，反而关不干净。

**当前实现（稳定）**：`kill_dsh` 直接 `/F /T` 强杀，`open_dsh` 直接 `Popen` 不等待。
如果确实遇到拉不起来，手动删 `%APPDATA%\@deepseek-ai\dsh-desktop\lockfile` 即可。

## 七点二十一、2026-10-26：★★ "打开 DSH 拉不起来"的真正根因

> **代价最大的一次误判**。修了两天，中间走错四个方向，最后发现是**一个环境变量**。

### 7.21.1 现象

- 大肥鱼菜单「打开 DSH」→ 没反应
- **手动双击桌面快捷方式 → 能启动**
- 菜单等待 10 秒再点 → 仍然失败
- 菜单关闭后**立刻**手动启动 → 成功

`logs/dsh_launch.log` 里只有一行关键信息：

```
open_dsh: Popen 成功 pid=4404
verify: 进程已退出 退出码=0
```

**退出码 0、stdout/stderr 全空** —— DSH 自己静默退出了。

### 7.21.2 根因：`ELECTRON_RUN_AS_NODE=1`

```powershell
PS> Get-ChildItem env: | Where-Object { $_.Name -match 'ELECTRON' }
ELECTRON_RUN_AS_NODE = 1
```

DSH 给它的子进程环境设了 `ELECTRON_RUN_AS_NODE=1`。

完整因果链：

```
DSH 启动插件 / 工具子进程 → 设 ELECTRON_RUN_AS_NODE=1
        ↓
大肥鱼（pythonw）继承该变量
        ↓
大肥鱼 Popen(DSh.exe) → DSH 也继承该变量
        ↓
Electron 见到 ELECTRON_RUN_AS_NODE=1 → 以**纯 Node 模式**启动
（不创建 GUI 窗口，只跑 Node 脚本，然后退出）
        ↓
退出码 0，无任何输出
```

**手动双击能成功**：explorer 的环境里没有这个变量。

### 7.21.3 为什么"更新前正常"

DSH 在 **2026-10-23 16:00 更新到 0.2.1-rc.3**，用户的问题正是从那天开始。
旧版不响应 `ELECTRON_RUN_AS_NODE`，新版响应了。

> 这正是用户一开始就给出的线索："这和更新有很大关系，更新前都是正常的"。
> **应该更早沿着这条线索查，而不是反复怀疑自己的代码。**

### 7.21.4 修复

`open_dsh` 启动前把 `ELECTRON_*` 从环境里剔除：

```python
removed_env = [k for k in list(env) if k.upper().startswith("ELECTRON")]
for k in removed_env:
    env.pop(k, None)
if removed_env:
    dsh_log("open_dsh: 已剔除环境变量 %r" % (removed_env,))

proc = subprocess.Popen([exe], cwd=base, env=env)
```

重试路径 `_verify_dsh_started` 同样处理。


| # | 当时的假设 | 实际 | 为什么错 |
|---|---|---|---|
| 1 | 双击代码引入了 bug | 无关 | 回滚后仍失败 |
| 2 | Qt 主线程 `sleep` 导致卡死 | 卡死是真的，但不是启动失败的原因 | 两件事混淆了 |
| 3 | `taskkill /F` 残留单实例锁 | 锁确实是问题之一，但**清锁返回 `[]`** 说明文件根本不存在 | 只解释了部分现象 |
| 4 | 优雅关闭 → 等进程退出 → 再打开 | DSH 子进程不响应 WM_CLOSE，2 秒内无效 | 加了复杂度，没解决问题 |

**决定性线索**是用户这句话：

> **"菜单等待十秒启动也无用"**

10 秒足以让任何锁/句柄释放，所以**不是时序问题**，只能是启动**方式**或**环境**问题。
这一句直接排除了方向 3 和 4。

### 7.21.6 保留的清理逻辑

虽然根因不是锁，但强杀后 `lockfile` **确实**会短暂残留（实测 `Remove-Item` 报
"正由另一进程使用"）。所以保留了：

- `close_dsh`：直接 `taskkill /F /T` 强杀 → `QTimer` 异步轮询确认退出 → `_clear_dsh_locks()`
- `open_dsh`：启动前若 `not is_dsh_running()` 则先清锁

> **已删除的冗余**：`soft_close_dsh()`（优雅关闭）与 `_wait_dsh_soft_tried`
> 两阶段逻辑——实测无效，反而拖慢关闭。

### 7.21.7 排查这类问题的方法论

1. **先看退出码**。0 = 程序自己决定退出；非 0 = 异常。
2. **对照"能成功的路径"**（手动双击）找环境差异：父进程、环境变量、命令行参数、cwd。
3. **环境变量优先怀疑 `ELECTRON_*` / `NODE_*`** —— Electron 应用对它们敏感。
4. **不要过早排除用户给的线索**（"更新后才出现"）。

### 7.22.3 四条安全边界

1. **只在 DSH 已运行时动作** —— 进程没起 → `bring_dsh_to_front()` 直接返回 `False`，绝不顺手拉起。

### 7.22.4 窗口识别要点（踩过两个真实坑）

**坑 1：IME 窗口被当成 DSH 主窗口**

### 7.22.5 前台提升的三级兜底

Windows 有"前台锁"：非前台进程调 `SetForegroundWindow` 会被静默拒绝。
双击时桌宠刚被点过、本就是前台进程，所以第 ① 级通常就成功；后两级是保险。

| 级别 | 手段 | 说明 |
|---|---|---|
| ① | 直接 `SetForegroundWindow` | 双击场景下够用 |
| ② | `AttachThreadInput` 挂到当前前台线程 | 跨进程常被拒绝，失败继续 |
| ③ | `keybd_event(VK_MENU)` 模拟按一下 Alt | 系统认为"用户在操作"，解除前台锁 |
| 最后 | `FlashWindow` | 仍失败就闪任务栏，不抢输入焦点 |

### 7.23.2 ★ 为什么没有照搬 whale-pet 的播放方式（重要，别重走）

用户一度怀疑"换成同样的播放模式就能丝滑"，实测**四条路全部走不通或代价过高**：

| 方案 | 实测结果 | 结论 |
|---|---|---|
| QtMultimedia 播 webm | 能解 VP9，但 `alpha=255 100%` → **透明通道丢失** | 否决 |
| 把 pp6 的 webp 序列转成带 alpha 的 webm | PyAV 19.0.1 编码侧声明的 yuva420p 被丢弃（回读 alpha min=max=255） | 否决 |
| QtWebEngine 播 webm | **可用**，半透明像素 84.3%，组件齐全 | 否决，但理由是"每只一个 Chromium 合成层，多开 30 只不划算" |
| Qt 原生 QPainter 变换 | 锐度 95.6~100.1%，0.253ms/帧 | ✅ **采用** |

**关键事实**：whale-pet 的 webm 本身是 `pix_fmt=yuv420p`（只有 3 个平面），alpha 藏在 VP9 的
**BlockAdditions** 里 —— 只有 Chromium 读得到，libvpx 编码侧写不出来。所以"把素材转成同样的 webm"这条路，
在不引入 Chromium 的前提下**物理上不存在**。

**结论**：whale-pet 的"丝滑"确实绑定 Chromium 合成层，不可单独移植；但它的**倾斜数学**（弹簧 + 脚底旋转轴）
和 **Q弹时序**是纯逻辑，可以完整搬过来 —— 实际效果已经做到用户认可。

### 7.23.3 ★ 帧撕裂的真正根因（排查了整整一轮）

用户反馈"之前做过了，帧撕裂特别严重，清晰度也变低了"（m00340）。

- **现象**：快速倾斜时角色边缘留残影。
- **排除的**：窗口裁剪（硬切比例恒 0，QPainter 旋转自带抗锯齿）、缩放算法（已用 Smooth）、
  预缩放再旋转（这影响**清晰度**不影响撕裂）、预乘 alpha、帧率（125Hz 连续重绘实测 124fps，A/B/C 三方案几乎相同）。
- **真凶**：窗口设了 `WA_TranslucentBackground` + `WA_NoSystemBackground`，**Qt 不会自动擦背景**；
  旧 `window.py.bak-jelly-154007` 的 paintEvent **没有清屏**。
- **对照实测**：不清屏 → 残影 710 像素、边缘过渡宽度标准差 15.96；清屏 → **0 像素**、14.68。
- **修法**：paintEvent 开头
  ```python
  p.setCompositionMode(QPainter.CompositionMode_Source)
  p.fillRect(self.rect(), Qt.transparent)
  ```
  **这条不能删**，删了撕裂立刻回来。

### 7.23.4 清晰度：预缩放与「变换源」的取舍

**第一轮（2026-10-29）—— 结论后来被推翻了，但过程有参考价值：**

| 做法 | Tenengrad 锐度 | 单帧耗时 |
|---|---|---|
| 先把图缩到目标尺寸，再旋转 | **67.6%**（二次重采样） | 0.096ms |
| 保留原图，`drawImage(dst_rect, cur_pix, src_rect)` 一次复合变换 | **95.6~100.1%** | 0.253ms |

0.253ms 只占 60fps 预算（16.7ms）的 1.5%，**不是瓶颈**，所以当时选了清晰的那条。
连带改动：`loader.py` 不再 `img.scaled()`；`frame_cache` 缓存键去掉尺寸 `(name, 0, 0)`；内存 357MB → 331MB。

**但常态（无变换）不能一直用原图**：加了 `_static` 判断 —— 无倾斜/无Q弹/无squash/无镜像时走
`_scaled_frame_for_paint()` 缓存路径，1:1 贴图 0.070ms/帧（30 只 5.0%，和改造前持平）；
只有真的在变换时才用原图。`tests/test_sway_and_perf.py` 守着这条。

**第二轮（2026-10-30）—— 用户反馈"开了摇晃，鼠标一靠近还是会明显变糊"：**

第一轮的 Tenengrad 指标**被骗了**。它是梯度能量，旋转带来的边缘振铃（暗边）会把分数顶上去，
所以"95.6%"其实是"更锐但更脏"。真机放大 6 倍看：优化前头发高光斑块边缘发毛、白蕾丝花边糊成一片，
而静止时（1:1 贴图）干净利落 —— 这个落差就是用户体感到的"一靠近就变糊"。

根因是**缩小倍数**。Qt 有两条截然不同的缩小路径：

| 路径 | 触发方式 | 缩小时的行为 |
|---|---|---|
| 面积平均 | `QImage.scaled(..., SmoothTransformation)` | 每个源像素都参与，**不丢信息** |
| 双线性 | `QPainter.drawImage(dst, src, ...)` + `SmoothPixmapTransform` | 只采目标点周围 **2×2** 邻域 |

scale=0.45 时是 640×360 → 288×162，**缩小 2.22 倍**。双线性在这个倍率下大量源像素被跳过 →
混叠 → 边缘发糊发脏。静止时走的是面积平均，倾斜时走的是双线性，两条路径画质天生不一致。

**修法**：变换帧不直接用原图，先用面积平均缩到 **1.5× 显示尺寸**（432×243），再交给
`drawImage` 做「缩 0.67 倍 + 旋转」这一次重采样。小倍率缩放的双线性损失很小，面积平均又把
源像素吃干了。常量 `TILT_SRC_SUPERSAMPLE = float(os.environ.get("DSH_PET_TILT_SUPERSAMPLE", "1.5"))`。

配套坑：`_scaled_frame_for_paint()` 的缓存上限原本是 `len(c) > 2` 就清空，而倾斜时会在
「288 显示图」和「432 变换源图」两个尺寸之间来回请求 → **互相清空、帧帧重算**。已放宽到 `> 6`。

实测（scale=0.45，3.5°）：

| | 梯度能量 | 绘制耗时（中间图已缓存） |
|---|---|---|
| 静止（基准） | 42.29 | 0.070ms |
| 优化前（原图直接变换） | 47.76（振铃，视觉发脏） | 0.119ms |
| 优化后（1.5× 面积平均中间图） | 41.18 | 0.107ms |

**优化后梯度略低于静止，这是旋转重采样的固有代价，不是退化** —— 画面干净、无暗晕才对。
中间图生成 0.46ms 一次，按 24fps 换帧算约 1.1% 单核，且缓存命中后不再重算。

**第三轮（2026-10-30，用户回：「依旧明显模糊」）—— 现场旋转这条路走不通，改成预渲染：**

前面两轮都在优化"现场旋转"的质量。但有个前提被忽略了：

> **静止时是 `drawImage(int(x), int(y), 缩放图)`，整数坐标 1:1 贴图，零重采样、像素完美。
> 只要角度**每一帧都在变**，Qt 就必须每帧重新重采样一次。无论重采样做得多好，
> 都追不平"零重采样"。这就是"一靠近就糊"的物理上限。**

所以第三轮换了思路：**把旋转结果预先算好，缓存成 pw×ph 的图；之后每帧只做 1:1 整数贴图。**

```python
TILT_CACHE_STEPS = int(os.environ.get("DSH_PET_TILT_STEPS", "24"))      # 角度档数
TILT_CACHE_SUPERSAMPLE = float(os.environ.get("DSH_PET_TILT_CACHE_SS", "2.0"))
```

paintEvent 在 `painter.save()` **之前**插快路径（纯倾斜、无 Q 弹、无 squash、不在淡化中）：

```python
_q = round(self.tilt.cur * TILT_CACHE_STEPS) / float(TILT_CACHE_STEPS)
_cimg = self._tilt_rendered(_q, mirror, pw, ph)      # 命中就返回
_dx = int(round(self.tilt.offset_x))
painter.drawImage(int(x) + _dx, int(y), _cimg)       # 1:1 整数贴图，零重采样
return
```

`_tilt_rendered(quant, mirror_on, pw, ph)` 负责生成：`QImage(pw, ph, Format_ARGB32_Premultiplied)`
→ `fill(transparent)` → 镜像（如需）→ 绕 `(pw/2, pivot_y)` 旋转 `quant * TILT_MAX_DEG`
→ 把 `_scaled_frame_for_paint(pw*2, ph*2)` 的 **2× 面积平均中间图**贴进来。
缓存键 `(id(cur_pix), quant, mirror, pw, ph)`，**帧一换就把别的帧的条目全清**。

★ **缓存图只含旋转，不含横向位移** —— 位移由调用方 `int(round(offset_x))` 整数叠加。
这样缓存只按角度分档，不必为每个位移量再存一份（否则 24 × 11 = 264 张）。

实测（scale=0.45，3.5°）：

| | 梯度能量 | 说明 |
|---|---|---|
| 静止（基准） | 42.29 | 1:1 贴图 |
| 第二轮（现场旋转 + 1.5× 中间图） | 42.40 | 视觉仍比静止软 |
| **第三轮（预渲染缓存 + 1:1 贴图）** | **44.06** | 与静止**肉眼无差**，只有角度不同 |

成本（`工具/倾斜缓存成本.py` 测）：

| 项 | 数值 |
|---|---|
| 生成一张（2× 超采样 + 旋转） | 1.15ms |
| 命中一次（查字典） | 0.0029ms（几乎免费） |
| 一帧存满 49 个角度档 | ≈ 8.7 MB |
| 按 24fps 每帧一次未命中折算 | 2.15% 单核 |

★ **测量踩坑**：第一版脚本在循环里写 `pet.cur_pix = QImage(str(f))`，把 webp 解码（约 3ms/张）
算进了渲染成本，得出"8.16% 单核"的虚高数字。正确做法是先 `DECODED = [QImage(...) for f in frames]`
把解码摘出去，再循环。

**★ 但第一版缓存实现仍然是糊的（用户回：「摇晃开启后清晰度有明显降低」）：**

第一版在 `_tilt_rendered` 里把 `_scaled_frame_for_paint(pw*2, ph*2)` 的 576×324 直接
`drawImage` 到 288×162 的画布上 —— 那正是**双线性缩小 2 倍**，混叠原样回来，只是外面
套了一层缓存。放大看跟旧的现场旋转一样脏。

正确顺序（现在代码里就是这个）：

```
1. 面积平均：640×360 → 576×324     _scaled_frame_for_paint(tw, th)，每个源像素都参与
2. 只旋转：576×324 → 576×324 画布   painter 只 rotate，**不缩放**（1:1）
3. 面积平均收尾：576×324 → 288×162  canvas.scaled(pw, ph, SmoothTransformation)
```

**任何一步只要让 drawImage 做缩小，就退回 2×2 双线性、跳过源像素。**
这和 GPU 的 mipmap 是同一个道理：先把多余像素用面积平均吃掉，再做几何变换。

实测梯度（scale=0.45，3.5°，静止基准 42.29）：

| 做法 | 梯度 | 目测 |
|---|---|---|
| 静止 | 42.29 | 基准 |
| 旧：现场旋转（drawImage 缩 2.22 倍） | 47.76 | 边缘灰黑镶边，脏 |
| 第一版缓存（drawImage 缩 2 倍后再贴） | 44.06 | 同上，没救回来 |
| 缓存 SS=1.0（只旋转） | 37.11 | 略软 |
| **缓存 SS=2.0（旋转 + 面积平均收尾）** | **40.59** | **与静止肉眼一致** |

★ 梯度越高不等于越清晰 —— 混叠和振铃都会把梯度顶上去。**只有"和静止并排看"才是判据。**
后来找到更稳的指标：**高频占比** = alpha 加权灰度减 3×3 均值后的残差占比，不被振铃骗。

**第四轮（2026-10-30）—— 用户澄清「我一直都是在大 1.0 的状态的」，前三轮的前提整个错了：**

前三轮全部按 scale=0.45 调，而用户实际一直用 **1.0（大）**。1:1 显示时：

| 做法 | 高频 | 保留率 |
|---|---|---|
| 静止（基准，零重采样） | 10.19% | 100% |
| 旧：1.5× 超采样 + 双线性 | 6.25% | **61%** |
| 去掉放大（原图直接双线性旋转） | 7.27% | 71% |
| **PIL BICUBIC 预渲染** | **9.85%** | **96.6%** |

★★ **决定性事实：超采样只在「显示尺寸 < 原图」时有意义。**
scale=1.0 时 `pw × 1.5 = 960 > 640`，那是把原图**放大**再缩回 —— 零新信息、多两次插值，
反而比不超采样还差。所以两处 `tw/th` 都加了 `min(..., self.cur_pix.width())` 钳制。

★★ **第二个事实：Qt 的 `drawImage` 只有 2×2 双线性，撑不住 3.5° 旋转（71%）。**
支撑域 4×4 的 BICUBIC 能到 96.6%，肉眼和"不摇晃"看不出差别。

修法（两条都已落地）：

1. 中间图尺寸钳制到不超过原图 —— 1:1 时直接拿原图旋转
2. `_tilt_rendered()` 优先调 `_tilt_rendered_pil()`：PIL `Image.AFFINE` + `BICUBIC`

```python
try:
    from PIL import Image as _PIL_IMAGE      # 可选依赖，没装就退回 Qt 双线性
except Exception:
    _PIL_IMAGE = None
```

**坐标约定（这里踩过坑）**：PIL 的 AFFINE 把输出像素 `(x, y)` 映射到输入 `(a*x+b*y+c, ...)`，
其中 `(0, 0)` **就是第一个像素的中心** —— 实测 `offset=0` 时恒等变换与 NEAREST 逐像素完全一致，
`offset=±0.5` 会整体偏半像素。所以常数项里**不要额外加 0.5**。

成本（`工具/测摇晃帧耗时.py`）：

| 项 | 数值 |
|---|---|
| bicubic 生成一张（640×360） | 20.4 ms，只在换角度档时发生 |
| 命中缓存 | 0.38 ms |
| 缓慢扫过 0°→3.5°（48 帧） | 24 帧生成 + 25 帧命中，平均 10.2ms/帧 |
| 快速往返（147 帧） | 平均 3.1ms，仅 18 帧超 16.7ms（瞬时掉帧，无持续卡顿） |

PIL 是**可选依赖**：没装就自动退回 Qt 双线性（71%），功能不受影响，只是画质差一档。
调参：`DSH_PET_TILT_STEPS` 角度档数（24 档 = 0.146°/档）；`DSH_PET_TILT_CACHE=0` 关掉整条快路径。
对比图 `工具/输出/摇晃修复前后.png`（静止 / 修复前 / 修复后，NEAREST 放大 3.4 倍）。

### 7.23.5 锯齿：一个只在"倾斜归零那一帧"出现的 bug

### 11.4 单实例：不重复拉起

`plugin.js` 的 `ensureRunning()` 先 `GET http://127.0.0.1:3080/state`（700ms 超时）：

- 通了 → 记日志"复用，不重复拉起"，不 spawn；
- 不通 → 按 `projectDir` 找 `main.py`，**通过 WMI 拉起**（见 11.4.1）；
- 插件卸载时**只 kill 自己拉起的 child**，用户独立启动的实例保持原样。

#### 11.4.1 关键：必须用 WMI 启动，`detached:true` 不够

**现象**（2026-10-20 报）：独立双击 `启动桌宠.bat` 起的桌宠，DSH 退出后**活着**；
但被 DSH 插件拉起的桌宠，DSH 退出会被**连带关闭**。

**根因**：DSH host 进程处在一个 **Job Object** 里，且该 Job 带
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`。Job 是**继承**的——不管父进程用什么标志
`CreateProcess`，子进程都会归入同一个 Job（除非显式 breakaway）。

实测证据：

```
IsProcessInJob(pet 6140)  → IN JOB
IsProcessInJob(host 3640) → IN JOB
CreateProcess(CREATE_BREAKAWAY_FROM_JOB) → OSError WinError 5（拒绝访问）
```

- Node 的 `detached: true` 只设 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`，
  **不脱离 Job**，所以旧写法在 DSH 建 Job 之后就不再有效；
- `CREATE_BREAKAWAY_FROM_JOB` 需要 Job 开 `BREAKAWAY_OK`，DSH 没开 → 走不通。

**解法**：让**别的进程**去创建它。插件改用 WMI：

```js
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
  CommandLine = '"<python>" -u "<projectDir>\main.py"'
  CurrentDirectory = '<projectDir>'
}
```

由 `WmiPrvSE.exe` 执行创建，父进程不是 DSH → 不在那个 Job 里。实测：

```
WMI Create → ProcessId 18460
IsProcessInJob(18460) → no job
parent → 7796 (WmiPrvSE)
GET :3080/state → 200
```

实现要点（`plugin.js` 的 `launchViaWmi`）：

- `python` 若是裸命令名，先用 `where.exe` 解析成绝对路径
  （**必须用绝对路径** `%SystemRoot%\System32\where.exe`，DSH 的 PATH 可能精简过）
- PowerShell 也用绝对路径 `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`
- PowerShell 单引号字符串里的 `'` 要写成 `''`
- WMI 不可用时**回退到原来的 spawn**（能跑，只是 DSH 退出会被带走），并打警告日志

#### 11.4.4 ★ 两个附加坑（2026-10-20）

**坑 1：`where pythonw` 会命中 Microsoft Store 假壳**

```
%LOCALAPPDATA%\Microsoft\WindowsApps\pythonw.exe
```

这是商店应用的 shim，**不能真正执行 Python**（双击它会引导去装商店版）。
`where` 按 PATH 顺序返回多个结果，直接取第一个就中招。

修复：过滤掉 `\WindowsApps\` 路径，取后面那个真的：

```js
const first = list.find((p) => !/\\WindowsApps\\/i.test(p))
```

**坑 2：`ProcessStartupInformation` 在 `Invoke-CimMethod` 里不可用**

```
Invoke-CimMethod : 无法提供 .NET Framework 的 CimType
```

想用它传 `ShowWindow=0` 来隐藏控制台窗口，实测直接报错 → WMI 调用失败 →
fallback 到 spawn → 反而弹出控制台。**控制台窗口靠"用 pythonw"解决**，
pythonw 是 GUI subsystem，本来就没有控制台，不要靠启动参数。

同理 `启动桌宠.bat` 的 `where python` + 检查同目录 `pythonw.exe` 也有踩到
Store shim 的风险，改它时注意过滤。

#### 11.4.2 ★ 第一版 WMI 为什么"完全拉不起来"

第一次改动用的是 **`spawn` + `unref`**，结果 DSH **再也拉不起桌宠**。根因：

```js
const launcher = spawn(psExe, [...], { detached: true, stdio: 'ignore' })
launcher.unref()
return true                 // ← 问题在这
```

`spawn` 只表示"进程已创建"，**不代表 PowerShell 成功执行了 WMI**。
PowerShell 若因参数/策略/环境问题立即退出，代码仍返回 `true` → 既不拉起、
也不 fallback → 表现为"完全拉不起来"，且没有任何日志。

**修复**：改用 `spawnSync` 并确认 WMI 真的返回成功：

```js
const r = spawnSync(psExe, ['-NoProfile','-NonInteractive','-Command', ps], {
  encoding: 'utf8', timeout: 20000, windowsHide: true })
if (r.status !== 0) return false                        // → 触发 fallback
const m = String(r.stdout).match(/ReturnValue\s+(\d+)/) // Invoke-CimMethod 输出
if (m && Number(m[1]) !== 0) return false
```

同时补了 `logs/plugin.log` 文件日志（DSH 的 `ctx.logger` 在 GUI/主进程日志里不好翻，
排障只能靠猜），记录 `ensureRunning` 每个分支、`where` 结果、PowerShell 的
status/stdout/stderr。
