## 一、文件操作与工具坑（最痛的几条）

### 1.1 PowerShell 5.1 的 String.Replace 没有三参数重载

**错误写法**：
```powershell
$t = $t.Replace("旧", "新", 1)   # 想只替换第一处
```

**后果**：抛 `找不到"Replace"的重载，参数计数为:"3"`。如果这行在赋值链里（如 `$tail2 = $tail.Replace(...)`），
变量变 `$null`，后续 `WriteAllText` 写入空/半截内容，**文件直接被截断**。
本次会话真实发生：window.py 从 27996 字节被截到 6084 字节。

**正确做法**：
- 只替换第一处：`[regex]::Replace($t, [regex]::Escape($old), $new, 1)`
- 或改成"行号定位 + ArrayList.RemoveRange/InsertRange"（见 1.2）
- **任何 Replace 前先 Copy-Item 备份目标文件**

### 1.2 多行字符串 Replace 经常 miss

**现象**：明明 grep 到了内容，`$t.Contains($多行串)` 却返回 `$false`。

**原因**：
- CRLF / LF 混用（文件 `\r\n`，脚本写 `\n`，或反之）
- 行尾多余空格、tab/space 混用
- 中文全角/半角引号

**正确做法（本次会话最终采用）**：
```powershell
$raw = [IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)
$L = [System.Collections.ArrayList]@($raw -split "`r?`n")
$f1 = -1; for ($i=0; $i -lt $L.Count; $i++) { if ($L[$i] -match "锚点") { $f1 = $i; break } }
$f2 = -1; for ($i=$f1+1; $i -lt $L.Count; $i++) { if ($L[$i] -match "结束锚点") { $f2 = $i; break } }
$L.RemoveRange($f1, $f2 - $f1 + 1)
$L.InsertRange($f1, [string[]]$新行数组)
[IO.File]::WriteAllText($p, ($L -join "`n"), [Text.UTF8Encoding]::new($false))
```

### 1.3 大段替换直接用 Python 小脚本

PowerShell 处理多行 + 中文 + 正则太容易翻车。**大段替换用 Python**：
```python
import io
p = r"目标文件"
t = io.open(p, encoding="utf-8").read()
def rep(old, new, tag):
    global t
    if old in t: t = t.replace(old, new, 1); print("OK", tag)
    else: print("MISS", tag)
rep("""旧代码""", """新代码""", "改动1")
io.open(p, "w", encoding="utf-8").write(t)
```
Python 的 `str.replace(old, new, 1)` 三参数是原生的，`"""..."""` 不挑换行符。
**本次会话最后修 paintEvent 就是用的这个方案，8 处替换一次全中。**

### 1.4 写中文文件必须用 UTF8 无 BOM

```powershell
[IO.File]::WriteAllText($p, $text, [Text.UTF8Encoding]::new($false))
[IO.File]::AppendAllText($p, $text, [Text.UTF8Encoding]::new($false))
```

- `Set-Content -Encoding UTF8` 在 PS5.1 会带 BOM，Python/Qt 读可能出问题
- `Add-Content` 处理中文路径容易崩，别用

### 1.5 动文件前先备份

```powershell
Copy-Item -LiteralPath $p -Destination ($p + ".bak-" + (Get-Date -Format "HHmmss")) -Force
```

本次会话因为没备份，window.py 被截断后**没有干净的原版可回滚**，只能靠 pycache 残余 + 手工续写恢复，浪费了很多轮。

## 二、架构与算法坑

### 2.1 Boids 只调制，不产生位移（最容易搞反的一条）

**错误认知**：重叠了就"推"宠物走。

**pet / dafeiyu 的正确架构**：
```
随机抽签 → 抽到漫游池
  → 算 overlap
  → 由 overlap 算 speedUp（越挤越快）
  → 得到 want_dist = baseDist × speedUp
  → 用 want_dist 选 tier（step/crab/run）
  → steer_target(距离, 合力, 墙斥) 得 target 点
  → 播放该移动动作，动作播放期间逐帧朝 target 缓动
```

**关键**：没有漫游动作就没有位移。Boids 只决定"这趟走多远、往哪个方向"，
**不能单独驱动窗口 move()**。否则会出现"不播动作也在飘"的鬼畜现象。

`tick_flock` 的正确职责：**只检测** overlap 是否超过硬阈值（0.8），超了就**请求换动作**，
不在里面做位移。

### 2.2 overlap 必须用身体框，不能用窗口

**错误做法**：`overlap_ratio(cx, cy, self.width()//2, self.height()//2, ...)`

窗口是 640×360，身体只占中间一小块（BODY_BOX ≈ 220,88,200,225）。
用窗口算，两只隔着大半个屏幕就判成"重度重叠"，斥力爆炸、宠物乱飞。

**正确做法**：
```python
bx, by, bw, bh = BODY_BOX
cx = self.x() + (bx + bw/2) * scale
cy = self.y() + (by + bh/2) * scale
half_w = bw * scale / 2
half_h = bh * scale / 2
```

### 2.3 overlap 是逐只相加，可以破表（>1）

十只叠成一摞时 overlap 应该 ≈ 9，而不是"逼近但小于 1"。
否则"挤成一团"和"两只相碰"在概率函数里看起来一样，散不开。

```python
acc = 0.0
for m in mates:
    d = hypot(...)
    if d < 2*r: acc += max(0, 1 - d/(2*r))
return acc   # 可以 > 1
```

### 2.4 镜像方向：素材基准朝左，朝右才翻转

pet 的规则（sprite.js L543 / L904）：
```js
el.style.transform = this.facing === "right" ? "scaleX(-1)" : ""
this.facing = dir >= 0 ? "right" : "left"
```

即：**位移向右 → facing=right → 翻转**；向左 → 不翻转。
素材原图（原地左转奔跑第 80 帧）确认是**朝左**的立绘。

**本次会话的 bug**：只给群体漫游分支加了 `_apply_facing`，
**单体模式的 move 分支漏了**，导致"小部分对、大部分反"。
凡是会移动的分支，生成 target 后都要调一次 `_apply_facing(dir >= 0)`。

### 2.5 完全重叠时合力为 0，必须 360° 随机

`flock_force` 对 `dist < 2px` 的邻居直接 `continue`（防除零）。
十个副本全叠在屏幕中心时，**合力恒为 0**。

如果这时让方向"继承 facing"，一群 facing 都是 left → **齐步往左跑**。
必须判 `has_force == False` → 用 360° 全角度随机：
```python
ang = random.uniform(0, 2*math.pi)
tx = cx + math.cos(ang) * want_dist
ty = cy + math.sin(ang) * want_dist
```

### 2.6 二维逃避：上下也要做

只做水平排斥，宠物会一路被推到屏幕上下边缘，
卡在 y 边界上**堆成一条水平线**（dafeiyu 第七轮实测结论）。

`wall_repel` 必须左右上下四面都算，纵向位移量 = `distance × (push_y / mag)`。

## 三、性能与渲染坑

### 3.1 渲染方式：QLabel.setPixmap 是性能杀手

**错误做法**：`QLabel` + 每帧 `setPixmap()`。
`setPixmap` 会触发 Qt 内部的 layout 计算 + repaint，
10 只 × 24fps = 每秒 240 次布局计算。

**dafeiyu 的成熟做法（70 只不卡）**：
```python
def paintEvent(self, ev):
    painter = QPainter(self)
    painter.setRenderHint(QPainter.SmoothPixmapTransform, True)
    painter.drawPixmap(QRectF(x, y, pw, ph), self.cur_pix,
                       QRectF(0, 0, self.cur_pix.width(), self.cur_pix.height()))
```

要点：
- 只存**原始帧** `self.cur_pix`，不预缩放
- 缩放交给 `drawPixmap(QRectF目标, pixmap, QRectF源)` 的硬件合成
- 切帧只改 `self.cur_pix` + 调 `self.update()`

**注意 `QRectF` 在 `QtCore`，不在 `QtGui`**：
```python
from PySide6.QtGui import QPainter      # 对
from PySide6.QtCore import QRectF       # 对
from PySide6.QtGui import QRectF        # 错！ImportError
```
写错会导致 paintEvent 每帧抛异常，窗口一片空白但又不报错到界面上。

### 3.2 预缩放全部 241 帧 = 内存炸弹

最初实现：`on_loaded` 里把 241 帧全部 `scaled()` 一份存 `pms_disp`。
单只占用 ≈ 241 × 480×270×4B ≈ 125MB，10 只 ≈ 1.2GB，GC 一跑就卡。

**正确做法**：不预缩放（交给 paintEvent），或按需 + LRU 缓存。

### 3.3 LRU 缓存容量必须 ≥ 一个动作的帧数

**错误做法**：LRU 上限 32 帧。
动作有 241 帧，顺序播放时每一帧都是新 idx，
**命中率恒为 0**，等于每帧都在做一次平滑缩放。

**正确做法**：上限 ≥ 241（整个动作一次性缓存，播完一轮后全命中）。
或者干脆按 3.1 用 paintEvent 硬件缩放。

### 3.4 定时器堆叠

每只宠物如果各自带这些定时器：

| 定时器 | 周期 | 10 只合计每秒 |
|---|---|---|
| 帧动画 timer | 41.7ms | 240 次 |
| hit_timer（鼠标悬停） | 30ms | 333 次 |
| flock_timer | 100ms | 100 次 |
| state_timer（DSH 状态） | 500ms | 20 次 |

**优化方向**：
- `hit_timer` 改成**模块级单一定时器**，遍历 `ALL_PETS` 统一检测
- `state_timer` 只让主实例（spawn_idx==0）轮询
- 光标 `setCursor()` 只在状态变化时调（加 `_cursor_state` 去重）
- Win32 的 `winId()` 缓存成 `self._hwnd`，别每次都调

### 3.5 QGuiApplication.primaryScreen() 别在 tick 里反复调

每次调用都要走 Qt 的平台层。缓存起来：
```python
_SCR_CACHE = [None]
def _scr():
    if _SCR_CACHE[0] is None:
        _SCR_CACHE[0] = QGuiApplication.primaryScreen().availableGeometry()
    return _SCR_CACHE[0]
```
（窗口大小/缩放变化时需要清缓存，目前固定屏幕场景够用。）

### 3.6 QPixmap.fromImage 是实测最大热点

cProfile 结果：4820 次调用累计 0.776 秒（占 3 秒采样的大头）。
这是 LoadThread 里把 QImage 转 QPixmap 的开销。

优化：
- LoadThread 里直接产 QPixmap（需注意 QPixmap 只能在主线程创建 → 改成 `QImage` 传回主线程后转）
- 或减少切换动作频率（不要每个动作播完立刻换，加最短停留时间）
- 或复用缓存：同一个动作第二次播放时直接用缓存，不再走 LoadThread

## 四、工作方法与教训（最值钱的部分）

### 4.1 遇到问题先摸成熟方案，别闭门造车

**本次会话最大的浪费**：性能问题反复猜、反复试，
最后才发现 dafeiyu（同样是 PySide6，能跑 70 只）早就有成熟实现，
看一眼 `paintEvent` 就解决了。

**规则**：
- pet-pyside6 是移植项目，上游有 **pet（Electron）** 和 **dafeiyu（PySide6）** 两套成熟实现
- 任何"该怎么做"的问题，第一反应应该是**去读上游代码**，不是自己设计
- 路径：
  - `~/.dsh/profiles/desktop/node_modules/dsh-pet/src/shared/flock.ts`（涌现算法）
  - `~/.dsh/profiles/desktop/node_modules/dsh-pet/runtime/electron-helper/shared-core.js`（打包后的完整实现）
  - `~/.dsh/profiles/desktop/node_modules/dsh-pet/runtime/electron-helper/sprite.js`（渲染/漫游/镜像）
  - `dafeiyu/runtime/helper.py`（PySide6 渲染，70 只不卡）

### 4.2 同一方案失败 2 次，立刻换类别

本次会话在 PowerShell 多行替换上连续失败 **5 次以上**（P1 miss、P2 miss、文件截断…），
每次都是"再调整一下字符串就好了"，结果越搞越糟。

**规则**：
- 同一个操作方式失败 2 次 → 必须换类别（PS 多行 → 行号定位 → Python 脚本）
- 换类别的成本远低于继续调参

### 4.3 改完必须实测，静态 grep 通过 ≠ 能跑

本次多次出现：grep 全部命中、py_compile 通过，一跑就 NameError。
典型：`overlap_ratio` 的 import 被前一次改 import 行时覆盖掉了，
grep `def overlap_ratio` 在 flock.py 里能找到，但 window.py 里没 import。

**规则**：
- 改完至少跑一次 `py_compile`
- 涉及运行时行为的，写个临时脚本实际建窗口跑几秒，打印关键状态
- 读 stderr，别看 stdout 正常就以为没事（Qt 的 paintEvent 异常只进 stderr）

### 4.4 改 import 行要小心覆盖

本次事故：用 `$t.Replace("from src.shared.flock import ...旧...", "...新...")`
替换 import 行时，新行漏掉了 `overlap_ratio`，导致运行时 NameError。

**规则**：改 import 行时，先把该模块所有 `def ` 列一遍，
确认新 import 行包含所有被引用的名字。

### 4.5 用户说"卡"，先要数据再动手

本次会话反复在"猜瓶颈"上浪费时间（先猜内存、再猜窗口数、再猜定时器）。
正确顺序：
1. 先测 CPU 占用（`(Get-Process -Id PID).CPU` 前后差值）
2. 再上 `cProfile` 看 top 函数
3. 再对照成熟方案看它怎么做的
4. 最后才改代码

### 4.6 不要擅自降帧率/降画质

本次一次错误决策：为了性能把 24fps 降到 15fps 并改用全局定时器，
被用户明确否掉（"不准降低帧率和画质"）。

**规则**：性能优化只能在"不牺牲观感"的前提下做：
- 减少重复计算 ?
- 缓存 ?
- 换渲染方式 ?
- 降帧率 ?
- 降分辨率/降画质 ?
